# 公网访问方案 · Cloudflare Tunnel 能不能塞进安装包

结论先说：**能做，值得做，但它属于"服务器侧的一个可选开关"，不是"客户端安装包的功能"**；
而且它的最大价值不是"让外面能访问"，而是**给 M10 的企业模式一个稳定的 https 地址**——
两件事合起来才成立。另外有一条前置现实必须先接受：**Cloudflare 边缘在国内的可达性不稳定**，
所以它不能是唯一路径，只能是三条路径之一。

本文只给方案与判据，未动实现。所有数字都是本机实测或产品里现成的配置项，不是估的。

---

## 1. 它真正解决的问题

用户说的"公网使用"其实混着三个不同需求，解法不一样：

| 需求 | 谁需要 | 隧道是不是正解 |
|---|---|---|
| A. 公司内同事能连到那台服务器 | 局域网即可 | **不是**。现在就要填 IP，痛点是"填 IP"，属于 M10 企业模式 |
| B. 出差/家里的员工也能连回来 | 没有公网 IP、宽带在 CGNAT 后面 | **是**，这是隧道唯一无可替代的场景：不打洞、不配端口映射、不要求有公网 IP |
| C. 干脆做成对外 SaaS | 多租户 | **不是**。单进程单机纵向扩展（`docs/adr/001-single-process-model.md:27-28`），一个隧道改变不了这个 |

**B 场景的真实形态**（也是我认为最该做的产品形状）：
一个 5–30 人的小团队，没有服务器机房，就一台常开的 PC。
```
一台 PC 装 zcagent（本机模式，自带服务） → 开一条命名隧道 → 得到 https://zc.jiuyeke.cn
      ↓
其余同事装 zcagent，首启选「接入公司服务器」，填这个地址
```
这条链上：
- 隧道替掉了"路由器端口映射 + 公网 IP + 动态 DNS + 证书"四件普通人做不成的事；
- **顺带解决 M10 记下的两个坑**：https 之后浏览器是 secure context，
  剪贴板不再降级（`dashboard/src/utils/copyText.ts:2-16`）；也不用教用户配证书
  （产品自带的 ACME 路径 `infra/setup/tls/` 要求域名能解析到本机，隧道场景恰恰做不到）。

所以顺序上：**M10（双形态）是地基，隧道是地基上最值钱的那块砖**。先做隧道再做 M10，
就得到一个"外面能打开但同事的客户端连不上"的半成品。

## 2. 事实与约束（实测）

### 2.1 二进制本身

| 项 | 实测值 |
|---|---|
| `cloudflared-windows-amd64.exe` | **55,365,048 字节（52.8 MB）** |
| `cloudflared-linux-amd64` | **40,129,756 字节（38.3 MB）** |
| 许可证 | **Apache-2.0**（GitHub API 与仓库 LICENSE 双确认）→ 可以再分发，**必须随包带声明** |
| 体积对照 | 现在 z10 桌面包 zip = 233,921,049 字节（含刚内置的 node +37.3 MB）。再加 52.8 MB ≈ **+23%** |

体积判断：内置到"每个包都带"是 **+23%**，比 node 那次(+20%)更贵，而它是**纯可选功能**。
所以建议**不无脑内置**，见 §4.1。

### 2.2 两种隧道，能力差别很大

| | Quick tunnel `cloudflared tunnel --url http://127.0.0.1:8088` | 正式命名隧道 |
|---|---|---|
| 需要 Cloudflare 账号 | 否 | **是** |
| 需要自己的域名 | 否 | 是（域名要在该账号下） |
| 地址 | `https://<随机>.trycloudflare.com`，**每次重启就换** | 固定，如 `zc.jiuyeke.cn` |
| 能不能放生产 | 官方明说不建议，且有速率/带宽限制 | 可以 |
| 落地成本 | 起进程 + 从它的输出里抓 URL | 登录换证书（浏览器 OAuth）或 API Token → 建 tunnel → 写 ingress → 加 DNS CNAME → 存凭证文件 |
| 适合我们哪一档 | 「先试试 / 演示」 | 「公司正式用」 |

**给员工填 IP 这件事，quick tunnel 帮不上忙**——地址每次重启都变，同事的客户端配置就废了。
所以 B 场景要可用，**必须走命名隧道**；quick tunnel 只能当"我看看这东西长什么样"。

### 2.3 产品现状里与"暴露到公网"直接相关的几项

已经有的保护：
- 默认只监听 `127.0.0.1`（`config.py:126`），开隧道是**显式**动作，不是改默认。
- `enable_api_docs` 默认 `False`（`config.py:135`）→ `/api/docs` 不会白送一张接口清单。
- 首启未完成时有 `setup_lockdown` 中间件（`api/middleware/setup_lockdown.py:15-41`）挡所有 `/api/`。
- 登录侧有验证码体系（`captcha` 权限键）与账号锁定/解锁（`unlock-login`）。
- 已有 TLS/ACME 能力（`infra/setup/tls/`、`/admin/tls/*`）。

必须正视的暴露面：
- **专家能碰本机**：`local_shell` 后端、终端、浏览器、远程桌面。认证一旦被绕过，等于主机 RCE。
  这不是"泄露几个文件"级别的风险。
- `GET /api/providers` 把 `api_key` **原样返回给浏览器**（`api/routers/providers.py:134`），
  任何登录用户可取。公网多用户下这是既有设计，不是隧道引入的，但暴露后后果更实际。
- `providers.api_key` 明文落盘（`001_initial.sql:52-63`）。
- 聊天是 WebSocket + 流式（`/api/agents/{id}/chat/ws`）：cloudflared 支持 WS 与流式，
  但**必须实测长连接**——我们已经有过"合法回复会持续推流 300 秒以上"的经验，
  中间任何一环设 100 秒空闲超时都会表现为"话说到一半断了"。
- 上传受 `max_upload_mb` 限制（`config.py:144`），Cloudflare 免费计划请求体上限 100 MB，
  两边取小值，且**超限时报什么错要实测**（隧道层的 413 和本地 413 长得不一样）。

### 2.4 国内可达性（最容易被忽略的一条）

`trycloudflare.com` 与 Cloudflare 边缘在国内的可达性**不稳定**，且随运营商/时间波动。
这决定了三件事：
1. 它不能是唯一路径（否则客户报"打不开"我们无从下手）；
2. 开隧道时必须**当场验证**（起完隧道立刻从本机走一遍 https 探活），不能只信子进程没退出；
3. 文档要写清"这是给没有公网 IP 的团队的备选路径，有公网 IP 优先用第 6 节的方案"。

## 3. 开启前必须过的硬门（不满足就不给开）

这是整个方案里最重要的设计：**开关本身不是风险，无门槛地开才是**。

| # | 硬门 | 现成机制 | 缺什么 |
|---|---|---|---|
| G1 | 已完成首启向导且设了管理员口令 | `OCTOP_REQUIRE_SETUP_PASSWORD` 默认 True（`config.py:137`） | 无 |
| G2 | 口令强度达标 | 现在只校验非空 | **要加**：公网模式下拒绝弱口令 |
| G3 | 登录验证码开启 | `captcha` 权限 + 验证码体系 | 无，需把它变成公网模式的必选项 |
| G4 | `enable_api_docs` 保持关闭 | 默认 False | 公网模式下**禁止**打开 |
| G5 | 公网模式下的"降权开关"：关掉终端 / 远程桌面 / 浏览器 / 本机 shell 后端 | 权限目录里已有 `terminal` / `desktop` / `mobile` / `browser` 键（`permissions.py:50-216`） | **要加**：一键把这些从所有角色里摘掉的"公网安全模式"，默认开 |
| G6 | 明确告知"流量经第三方边缘" | 无 | **要加**：勾选确认，并写进文档——这与 `README.md:3-4`「不出内网」的承诺直接冲突，必须显式打破，不能悄悄做 |
| G7 | 每次开/关/换址都进审计 | 有 `audit_log` 表 | 接一条事件类型即可 |

G5 值得单独说：小团队真正需要的是"同事能在外面问专家问题"，
不需要"外面能遥控这台机器的终端和桌面"。把后者默认关掉，
风险等级从"主机 RCE"降到"账号泄露"，这个功能才敢开。

## 4. 具体设计

### 4.1 二进制怎么来 —— 三条路，我推荐第三条

| 方案 | 做法 | 判断 |
|---|---|---|
| ① 全部内置 | 桌面包直接带 cloudflared | +23% 体积给 99% 用不到的功能。**不推荐** |
| ② 完全不内置 | 首次开启时联网下载 | 与 node 那次同样的毛病：内网/无公网 IP 的用户恰恰下载不动。**不推荐** |
| ③ **NSIS 可选组件 + 首次开启时下载并校验** | 安装向导里一个默认不勾的"公网访问组件"；没勾的用户在**内网里**（能连到服务器）点开启时才下载 | **推荐**：体积不惩罚默认用户；下载动作发生在"已经决定要暴露"的时刻，且失败能明确报错 |

无论哪条都要：钉版本（不要 `latest`）、带 SHA-256 校验、随包放 `LICENSE.cloudflared` 与
NOTICE 条目（Apache-2.0 要求）。校验和写死在一个 Python/Go 常量里，与 node 的 `NODE_VERSION` 同一处风格。

### 4.2 生命周期（新模块 `infra/tunnel/`）

- 一个子进程管理器：`start(mode, ...)` / `stop()` / `status()`，**复用已有的子进程与
  端口探活写法**（`infra/utils/ollama_manager.py` 就是同类形状，别另起一套）。
- 状态存 `settings` KV（与 `active_model`、预下载状态同一张表），字段：
  `enabled / mode(quick|named) / hostname / tunnel_id / pid / started_at / last_error / verified_at`。
- **URL 抓取**：quick 模式从 cloudflared 的日志里正则提取 `https://*.trycloudflare.com`；
  named 模式不抓——地址是我们自己配的，不依赖它的输出。
- 进程守护：崩溃后退避重启（1/5/30 分钟），连续失败 5 次则标记 `degraded` 并在 UI 顶部留一条红字，
  **不要静默重启到无限循环**（这是最容易变成"用户以为开着其实早死了"的形态）。
- 开完必须自证：拿到 URL 后**从本机发一次 `GET /api/health` 走公网回环**，
  成功才记 `verified_at`。探活失败就报"隧道已建立但公网访问未通过，请检查国内可达性"，
  而不是显示一个绿色的"已开启"。

### 4.3 两种模式的落地

- **Quick（试用）**：UI 上就一个按钮，起进程、抓 URL、显示"地址重启会变，只适合演示"。
  零账号、零配置，用来让人 5 分钟看到效果。
- **Named（正式）**：向导三步——
  ① 检测/输入 Cloudflare API Token（**只走 `Authorization` 头，不落库**，
  与 §3 的 G6 一起说明用途）；② 选账号下的域名 + 填主机名前缀；
  ③ 自动 `tunnel create` + 写 ingress(`http://127.0.0.1:<port>`) + `route dns add` +
  把凭证 JSON 存到 `OCTOP_HOME/tunnel/credentials.json`（`0600`，Windows 上说明 ACL 现实）。
  这一步与 M10 的"企业模式填服务器地址"天然接上：**填的就是这个固定域名**。
- 配置全部落在 `OCTOP_HOME` 下，不往用户家目录 `~/.cloudflared` 写（避免与用户自己装的
  cloudflared 互相踩）。

### 4.4 UI

- 位置：**设置 → 网络**（新页），不放"高级"——它的目标用户恰恰是不懂"高级"的小老板。
- 页面结构：一个大开关（默认关）→ 打开时先弹 G1–G7 的检查清单（不满足的项直接给"去设置"链接）
  → 通过后二选一（试用 / 正式）→ 显示当前状态、固定地址、一键复制、"公网安全模式"开关、
  最近错误。
- 顶部常驻一条状态提示（开着的时候），**不要只在设置页里显示**——
  "我以为关了其实还开着"是这类功能最坏的结局。

### 4.5 与既有能力的边界

- **不要**把它做成"改 `bind_host` 为 `0.0.0.0`"的包装——那是另一件事（局域网），
  且 M10 已经覆盖。
- **不要**动 Bridge（`docs/bridge.md`）：那是实例之间的联邦，与"别人访问我"是两回事。
- 与内置 ACME 的关系写进文档：有公网 IP + 域名能解析 → 用自带 TLS（无第三方依赖）；
  没公网 IP → 用隧道。二者互斥，UI 上给一次选择即可。

## 6. 替代方案对照（隧道不该是唯一答案）

| 方案 | 需要什么 | 国内可达性 | 谁该用 |
|---|---|---|---|
| 内网直连（现状） | 同事能路由到那台机 | 无问题 | 同一办公室，绝大多数场景 |
| 端口映射 + 动态 DNS + **自带 ACME** | 公网 IP（国内家宽普遍没有） | 最好（不经过第三方） | 有小公网 IP 的团队 |
| **Cloudflare Tunnel** | 一个 Cloudflare 账号（正式模式） | **不稳定** | 没有公网 IP、能接受第三方边缘 |
| frp 自建 | 一台已有公网 IP 的机器 | 好 | 公司已有云主机/机房 |
| Tailscale/ZeroTier 私网组网 | 各端装客户端 + 账号 | 一般～不稳定 | 只给固定几个人用，**安全性最好**（不暴露 HTTP 面） |

**产品姿态建议**：隧道做**内置**（因为它是唯一"零前置条件"的公网路径），
frp / Tailscale 只在文档里给指引、不内置——它们需要用户自己的基础设施，
内置了反而背锅。

## 7. 风险清单（照单全收再决定）

1. **暴露面从"内网"变成"互联网"**：专家能碰本机 shell/文件/浏览器，认证绕过 = 主机沦陷。
   → 靠 G5 公网安全模式 + G2/G3 收口；这是本方案最大的风险，不是隧道本身。
2. **与「不出内网」的产品承诺冲突**（`README.md:3-4`）。
   → 必须显式告知并勾选确认（G6），文档单列一节；不能悄悄开。
3. **国内可达性**：可能"配好了但连不上"。
   → 探活自证 + 文档 + 保留其它路径。
4. **长连接与流式**：WS/SSE 空闲超时导致"回答半路断"。
   → 上线前用一次 300 秒以上的真实长回复实测整条链，不要只看进程活着。
5. **quick 地址漂移**：重启换址，同事配置失效。
   → UI 上明写"演示用"，正式用必须走 named。
6. **第三方依赖与再分发义务**：cloudflared 版本要跟、校验和要维护、Apache-2.0 声明要带。
   → 与 node 同一处钉版本，纳入现有发版检查。
7. **凭据落盘**：named 模式要在本机存 Cloudflare 隧道私钥。
   → 只存 `OCTOP_HOME` 下、说明权限现实；Token 用完即弃，不落库。

## 8. 我的建议一句话

做，但按 **P0(M10 双形态) → P1(quick + 硬门) → P2(named)** 的顺序做，
二进制走"可选组件 + 首次开启时校验下载"而不是全量内置，
并且**把「公网安全模式」当成开启公网的前置条件**——
没有 G5 的公网开关，我不建议交付给任何真实客户。

### 与本文原稿不同的两个实测结论

1. **§4.2 说的"从 cloudflared 日志抓 URL"要配一个足够长的探活预算。** 实测地址打印后
   ~40 秒内本机解析该随机子域仍失败（边缘未生效 + 本地 DNS 负缓存），
   原稿暗示的"起完探一次"会把正常隧道判成坏。现在是 12 次 × 5 秒，且允许手动重验。
2. **`--header` 注入不存在**（`cloudflared tunnel --help` 实测无此标志，只有
   `--http-host-header` 改写 Host），所以"这个请求来自隧道"只能靠边缘加的
   `Cf-Connecting-Ip`。伪造它只会让自己被当成远程而降权，方向是安全的。
   另外 `--loglevel debug` 会把**每个请求头**写进日志（含凭据），所以启动参数里钉死 `info`。
